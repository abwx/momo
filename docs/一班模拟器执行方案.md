> **给执行 AI 的总指令**：按本文从 §0→§9 顺序实现。未写「允许」的能力不要加。不要整文件重写。每步完成后跑验证命令。默认用简体中文 UI。用户未要求时不要 git commit。  
> **产品已锁定**（2026-07-31）：幕后制作人 + 本命是否进一班；中量四期结构且每期有分班后果；制作人评级 + 本命成绩双结局；在现有模式上改；弱化伤害（降班/资源变少）；品牌名「一班模拟器」。

---

## 0. 一句话目标

把现有「团综制作人」主循环改成 **《一班模拟器》**：你仍是幕后制作人（机位/控评/开嗑可用），但每期结束按成绩 **重组一班/二班**，季终同时给出 **制作人评级** 与 **本命是否破局进一班**。

非目标：血腥淘汰、第一人称练习生、完整高会付费、推倒重写 `events.ts` 旧池、推倒 CSS。

## 1. 产品规格（已确认，禁止自行改向）

| 项 | 锁定值 |
|----|--------|
| 玩家身份 | 幕后制作人 |
| 核心焦虑 | 本命能不能进/留在一班 |
| 结构 | 四期：考核→任务→双人→释出（沿用 `groupShowProgram`） |
| 每期后果 | 期末按成绩重排班籍；一班末可降班，二班头可升班 |
| 话术 | 「降班」「资源变少」「席位紧张」；禁止「淘汰出道」「滚出」「去死」等 |
| 结局 | A) 制作人综合评级 SSS–F；B) 本命一班破局成功/失败 |
| 改造策略 | **在现有系统上挂接**，不新开平行游戏模式 |
| 品牌 | 对外名：**一班模拟器**（替换「团综制作人模拟器」等入口文案） |

### 1.1 分班规则（固定参数，可做成常量）

```ts
CLASS1_CAPACITY = 7
CLASS2 = 其余成员
```

- **期初**：可随机或按开局人气 Top7 进一班（推荐：按开局 `popularity` 排序取 Top7 为一班，其余二班）。
- **每期期末**：用 `assessmentScore`（考核分）全员排序；前 7 = 一班，其余 = 二班。
- **资源后果（弱伤害）**：
  - 一班：下期事件人气收益 `×1.0`（或小幅 `+`）
  - 二班：下期人气收益 `×0.85`，并在 UI 提示「曝光资源变少」
  - 考核：二班保留独立追分修正，领先一班成员的后续加分递减；不要复用人气乘数。
- **禁止**：成员离队、人数减少、永久死亡标记。

### 1.2 现有系统如何挂到突围（禁止砍掉再重做）

| 现有 | 突围语义 | 数值挂钩 |
|------|----------|----------|
| 机位 FOCUS 本命 | 给本命加考核戏份 | `assessmentScore[bias] +=` 与录制强度相关 |
| 机位 BALANCE | 群像补位 | 低考核分成员小幅加分 |
| 机位 DRAMA | 抓马博热度 | 焦点加分 + 轻微黑粉/dramaDebt（已有 season） |
| 控评 | 粉圈托举 / 反黑 | 影响下期考核修正或本命加成（保留粉盘） |
| 开嗑 | 双人舞台营业 | 选中 CP 对两人 `assessmentScore` 小幅加 |
| 镜头份/成片权/热搜位 | 当期操盘额度 | **保留机制**，文案可改为突围语境 |
| KPI | 本期目标 | 可保留；文案改为突围向（可选，非阻塞） |

## 3. 数据模型

### 3.1 新建类型 `SClassTrack.ts`

```ts
export type SClassKey = 'CLASS1' | 'CLASS2';

export interface SClassTrackState {
  capacityClass1: number;                 // 7
  classById: Record<string, SClassKey>;   // 全员必须有键
  assessmentScore: Record<string, number>; // 累计考核分，开局 0
  episodeResults: SEpisodeClassResult[];  // 每期快照，便于结算叙事
}

export interface SEpisodeClassResult {
  episodeId: string;
  rankedIds: string[];          // 本期按考核分排序
  promotedIds: string[];        // 二班→一班
  demotedIds: string[];         // 一班→二班
  biasClass: SClassKey;         // 本命当期班籍
}
```

### 3.2 必须提供的 S API（`SClassTrack.ts`）

| 函数 | 职责 |
|------|------|
| `SCreateClassTrackState(characters, capacity=7)` | 按开局人气 TopN 分班，考核分清零 |
| `SResetClassTrackState(...)` | 同 create 或原地重置 |
| `SAddAssessmentScores(state, deltas: Record<string, number>)` | 累加并钳位 ≥0 |
| `SGetClassMultiplier(state, characterId)` | CLASS1→1，CLASS2→0.85 |
| 考核竞争修正（内部） | 二班追分 `×1.15`；一班领先超过分数线后按档递减 |
| `SReshuffleClasses(state, episodeId, biasId)` | 按 assessmentScore 重排；写 episodeResults；返回结果对象 |
| `SIsBiasInClass1(state, biasId)` | boolean |
| `SGetClassRoster(state, characters)` | 供 UI：一班/二班名单 |

### 3.3 期末触发点（关键）

在 `App.vue`：

```text
confirmResultModal() 当 mode==='round'
  → nextEvent()
      → 若「刚完成的事件」是某期最后一个 eventId
           → SReshuffleClasses(...)
           → openNoticeModal 展示升/降班摘要（粉圈热报）
      → 若还有事件 → prepareEvent
      → 否则 → gameState='end'
```

检测「期完成」：复用/抽取与 `getCompletedEpisodeCount` 同类逻辑——  
`episode.eventIds.every(id => eventHistory 含 id)` 且本期结果尚未写入 `episodeResults`。

建议新函数：`SGetJustCompletedEpisode(program, eventHistory, episodeResults): ProgramEpisode | null`  
放在 `SClassTrack.ts` 或 `SSeasonSetup.ts`。

### 3.4 考核分来源（最小实现）

每节事件结算后（`applyEventResult` 末尾）：

1. 从 draft 人气变化推导基础考核增量（例如每人 `max(0, round(deltaPop * 0.5))`），或  
2. 更稳：事件结算后按「本节点名次」给固定分（第 1 名 +8 …），再叠加制作操作。

**必须叠加制作操作（现有系统挂钩）**：在 `applyRecordingControls` 成功后，或 `applyEventResult` 内读取本节 `recordingMode` / `focusCharacterId` / `studioLedger` 增量：

- FOCUS：`assessmentScore[focus] += 2 * intensity`
- BALANCE：人气低于均值的成员 `+= intensity`
- DRAMA：`assessmentScore[focus] += 3 * intensity`（可同步已有 drama 效果）
- 若本节有开嗑成功：对 pair `+= bondIntensity`
- 若本节有 SOLO 控评：对本命 `+= fanIntensity`

二班成员写入**人气 draft**时乘 `SGetClassMultiplier`（二班 `0.85`）。考核加分使用独立的竞争修正：二班追分更快，但一班领先者会递减，不能复用人气乘数。

### 7.2 四期文案

更新 `groupShowProgram.ts` 的 `title`/`summary`，强调每期结束「席位重排」：

1. 第一期：分组考核 → 首轮破局分班  
2. 第二期：清晨任务 → 班籍压力下的执行  
3. 第三期：双人舞台 → 搭档与资源  
4. 第四期：舞台释出 → 最终席位确认  

事件逻辑可先少改；**必须**保证期末 `SReshuffleClasses` 会跑。有余力再加强 RANKING 对 `assessmentScore` 的直接写入。
